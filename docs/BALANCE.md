# Симулятор баланса (BalanceSimulator, BalanceOptimizer)

Инструмент для тысяч быстрых «прохождений» без рендера, окон и сцены: ищет слабые места баланса по статистике, предлагает правки параметров и проверяет их на независимых сидах. Запускается из командной строки (Godot headless), результаты — JSON, CSV и Markdown, поэтому его может вызывать и читать Codex.

## Запуск

```
powershell -File tools\balance.ps1 <команда> [параметры]
```

| Команда | Что делает |
|---|---|
| `simulate` | массовый прогон профилей игроков → сводка, `runs.csv`, `summary.json/csv`, `.md` |
| `analyze` | `simulate` + эффективность каждого уровня каждого навыка, баланс оружия и вставок, дуэли с боссами (шанс победы по уровню героя), пробы эксплойтов |
| `optimize` | поиск изменённых параметров, проверка на других сидах, предложение в `balance/proposals/<имя>.json` |
| `prune` | убирает из предложения правки, без которых результат не ухудшается, и заново проверяет остаток на независимых сидах (`--overrides opt1`) |
| `compare` | два набора параметров на одних и тех же сидах (`--a base --b opt1`) |
| `report` | пересобрать Markdown из сохранённых `summary.json` (`--from <папка>/<имя>`) |
| `validate` | проверки соответствия игре, воспроизводимости, неизменности сохранений (`-Game` добавляет сверку с настоящим `Game`) |
| `targets` | записать предлагаемые целевые показатели в `balance/targets.json` |
| `apply` | записать в `Resources/Combat/tuning.tres` только `tuning.*` из предложения (`--confirm`, с копией файла) |

Общие параметры: `--n <прогонов на профиль>` (по умолчанию 1000), `--profiles novice,average,expert,optimizer`, `--seed`, `--threads` (0 — все ядра минус одно), `--name`, `--overrides <файл или имя предложения>`, `--targets <файл>`, `--max-hours`, `--model <файл model.json>`. `optimize`: `--iters`, `--lambda`, `--train`, `--valid`, `--groups tuning,boss,enemy,weapon,skill`, `--skill-bench`, `--target-loss`. Остановка долгого запуска: создать файл `balance/STOP`. Итог печатается строкой `[balance] RESULT {json}` — её читает автоматизация.

Результаты лежат в `balance/out/<имя>/` (в `.gitignore`), предложения — в `balance/proposals/`, цели — в `balance/targets.json`, калибровка профилей — в `balance/profiles.json` (необязательно, пример: `{"expert": {"DodgeSkill": 0.6}}`).

Производительность: ~1200 прогонов в секунду на 19 потоках (полное прохождение каждого), то есть 100 000 прогонов ≈ 1,5 минуты.

## Архитектура (`Scripts/Balance/`)

* `BalanceModel` — снимок данных **настоящей игры** в обычные классы без Godot: `tuning.tres`, `SkillDef` (уровни, цены, родители), `Db` (оружие, вставки, реликвии, синергии, чертежи), стоимость печи/фонаря/кирок (reflection на приватные таблицы `Game`), здоровье врагов (`Game.BaseHp`). Снимается один раз в главном потоке; дальше симуляция потокобезопасна. Реестр параметров (`Params()`) — единый список того, что вправе менять оптимизатор.
* `SimPlayer` — состояние героя и формулы игры (опыт, здоровье, урон, добыча, радиус света, бонусы навыков, условия открытия, эффекты оружия/вставок/реликвий/синергий).
* `CombatSim` — покадровый бой (шаг 0,05 с): сближение, цикл «пауза → предупреждение → удар», уклонение (зависит от времени реакции игрока и длительности предупреждения), конвейер урона `Hurt/OnHit` (ожог, замедление, заморозка, цепь, залп, пробой, взрыв, дуга, сифон, «серебряное лезвие», броня жука и стража, щит элитных и боссов), аура света, способности, восстановление. Боссы — цикл «пауза → действие» с весами по фазам.
* `Campaign` — прохождение от первого дерева до Источника Тьмы: добыча (время клетки, выход, цепная добыча), плавка, крафт, фонари, исследование мест, прокачка, боссы, смерти, отдых, «бросил игру».
* `Profiles` — четыре профиля **поведением**: реакция, уклонение и рывок, точность, отдых, готовность к боссу, выбор навыков (случайный / самый дешёвый / по сборке / жадный по пользе за цену), количество зажигаемых фонарей, использование вставок и реликвий. Шесть сборок (`Archetypes`) у эксперта.
* `Runner` — параллельный запуск; сид прогона = `f(общий сид, профиль, номер)`, поэтому результат не зависит от числа потоков.
* `Summary`, `Targets`, `Report` — статистика (доверительные интервалы Уилсона, ДИ среднего и медианы), поиск проблем, отчёты.
* `Bench` — контрольные схватки: эффективность каждого уровня навыка (парные разности при общих случайных числах), оружие, вставки, дуэли с боссами.
* `Optimizer` — (1+λ)-стратегия по диагнозу + случайные мутации; несколько целей одновременно (сложность по профилям, темп, разрыв между профилями, разнообразие сборок, плавность боссов, экономика, польза навыков). Обучающие и проверочные сиды не пересекаются; предложение считается подтверждённым только если потеря на проверочных сидах упала ≥ 5%.
* `BalanceCli` — команды; в `Game._Ready` стоит одна строка раннего выхода: при запуске с `-- balance …` мир не создаётся и сохранения не читаются.

## Целевые показатели

Предложены, **требуют согласования** (`balance/targets.json`, команда `targets`). Опорные точки темпа взяты из `PLAYTEST.md`: первый страж к 1 ч, маяк ≥ 3 к 3 ч, 5–10 ч у увлечённых игроков. Остальное — разумные значения: победа новичка 45–85%, среднего 75–96%, эксперта ≥ 90%; разрыв новичок/эксперт по времени 1,4–4×; оптимизатор не быстрее 65% времени эксперта; разброс сборок эксперта ≤ 10 п.п.; ≤ 3,5 попытки на босса; доля бросивших ≤ 25/10/5/5%.

## Проверка качества

* `validate` (CLI): данные модели совпадают с игрой; числа врагов, опыта, добычи и т. п. найдены в исходниках игры (если кто-то поменяет их в коде, проверка упадёт и таблицу нужно обновить); ключи эффектов `N("…")` существуют в игре; один сид → тот же результат; результат не зависит от потоков; сохранения `user://` не изменились; код симулятора не создаёт `Node` и не трогает сохранения; усиление врагов повышает смертность, дешёвый опыт повышает уровень.
* `LAMP_STAGE=balance` (в `tools/run_checks.ps1`) — **сверка с настоящим `Game`**: опыт на уровень 1…60, прирост здоровья, урон и скорость добычи по тирам и уровням, бонусы навыков при случайных уровнях, цены всех уровней всех навыков, родители, условия открытия, эффекты 60 случайных сборок (оружие + вставки + реликвии + синергии), здоровье и множитель урона врагов и боссов при трёх уровнях опасности, `DangerScale`, число ударов до смерти врага через настоящий `Game.Hurt`.
* Независимая проверка оптимизации: `optimize` сам прогоняет «до» и «после» на сидах, не участвовавших в поиске.

## Что симулятор НЕ воспроизводит (явно)

Деревня и жители (производство, шестерни, линзы), торговля и монеты, квесты и события, головоломки фонарей (только время дороги и стражи), фоновый жар/холод/дым, водные зоны, эффекты Эндгейма, кооператив, фонарь героя. Навыки производства (`Collector`, `SilverGears`, `ForgeHeat`, `AutoDrill`), видимости (`Sight`, `Optics`) и мостов помечены «не симулируется» — это не значит «бесполезны». Мир не генерируется: вместо него параметры `BalanceModel.A` (время на клетку, доля добычи вне света, шансы находок в местах…). Боссы Ash/Winter/Source смоделированы по структуре цикла и урону из кода, но без геометрии арены; щит Хранителя Зимы и Источника — цикл «головоломка → уязвимость» со временем головоломки по профилю.

**Абсолютные времена прохождения и абсолютные проценты побед зависят от допущений мира и от параметров профилей — это главная неопределённость.** Относительные сравнения (до/после, профили, сборки, навыки) надёжнее. Калибровку профилей (`balance/profiles.json`) и допущений мира нужно проводить по реальной телеметрии (`LAMP_DIAG`, `tools/summarize_diag.py`), как только она появится.

## Цикл для Codex

1. `simulate`/`analyze` → прочитать `RESULT` и `balance/out/<имя>/<имя>.md` (раздел «Найденные проблемы»).
2. `optimize --name run1` → `balance/proposals/run1.json`, отчёт `…/run1.optimization.md` с вердиктом «подтверждено / не подтверждено».
3. `compare --a base --b run1 --n 3000` для независимой проверки.
4. Человек согласует цели и предложение; `apply --overrides run1 --confirm` пишет только `tuning.*`, остальные параметры (навыки — `tools/gen_skills.py`, оружие — `Data.cs`, враги — `Game.Combat.cs`) меняются вручную.
5. После изменения игры — `validate -Game` (сверка), затем снова шаг 1.

## Первый прогон (2026-10-29, сид 1, модель на момент написания)

Файлы: `balance/out/baseline` (3000 прогонов на профиль + стенд навыков/оружия/боссов + пробы), `balance/out/opt3` (оптимизация), `balance/out/final_compare` (проверка на третьем наборе сидов, 4000 на профиль).

* **База:** новичок побеждает в 12% (87% бросают игру в Ледяном монастыре — Зеркальный страж принимает лишь 30% урона не-светового оружия), средний/эксперт/оптимизатор — 100%, медианы 3,6/1,5/1,4 ч. Боссы 2–3 почти не угрожают даже на низком уровне, Хранитель Зимы и Источник требуют ~28–31 уровень (скачок сложности).
* **Эксплойты (пробы):** «без фонарей» проходит игру за 81% времени оптимизатора (каждый фонарь поднимает `DangerScale` на 0,18); «нахрапом» (без подготовки и отдыха) выигрывает в 100% — смерть стоит ≤ 25 осколков и дороги.
* **Навыки:** Жатва теней — ≤ 0,8% на уровень; уровни 2–5 «Огненного лезвия» и «Рывка» бесполезны (длительность ожога и перезарядка насыщаются); «Заряд» (Overcharge) не даёт эффекта в схватках; «Клинок Хранителя» на ~140% сильнее медианы своего тира, посох «Пепельного стража» на ~46% слабее.
* **Оптимизация** (`optimize` → `prune`): 42 → 20 правок параметров, потеря функции цели на независимых сидах 170,8 → 2,4; новичок 12% → 78% побед (значимо), остальные профили без изменений победы, время +0,3…0,9 ч. Не решено в рамках изменяемых параметров: темп (эксперт 1,8 ч против цели 4 ч), «слишком лёгкий» средний игрок (100% при цели ≤ 96%), скачок сложности босса 5, Зеркальный страж. Это требует структурных решений (цена смерти, поведение фонарей, спавн, пути), а не только чисел `tuning.tres`.
* **Не применено:** ресурсы игры не менялись; предложение `balance/proposals/opt3min.json` — на согласование.
